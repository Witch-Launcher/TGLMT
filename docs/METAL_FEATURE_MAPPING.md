# METAL_FEATURE_MAPPING.md — OpenGL 1.0–4.6 → Metal on Apple A11 (iOS 11–16)

> **Scope.** For every OpenGL feature group, one classification, the Metal
> mechanism used, the semantic gap, and the evidence.
>
> **Companions:** `docs/METAL_A11_CAPABILITIES.md` (capability matrix + runtime
> probe), `docs/HARDWARE_LIMITATIONS.md` (the honest limit list),
> `docs/OPENGL_46_METAL_MAPPING.md` (the core-profile view),
> `docs/LEGACY_TO_METAL_MAPPING.md` (the 1.x fixed-function view — **not**
> rewritten here).
>
> **Hard rule of this document** (from `project/AGENTS.md` §6):
> `HARDWARE LIMITED` requires **(a)** a capability query or Apple documentation
> **and (b)** the emulation options considered with the reason for rejection.
> *"Metal has no such API"* is **never** sufficient. Every `HARDWARE LIMITED`
> row below therefore carries both, and no row is marked `HARDWARE LIMITED`
> without them.
>
> **Constraint from `project/AGENTS.md` §6 / D-018:** a geometry shader must
> have a **working emulation**; concluding `HARDWARE_LIMITED` for geometry
> shaders is **forbidden**. §3.5 below therefore specifies the emulation.

---

## 0. Classification scheme

| Class | Meaning |
|---|---|
| **DIRECT MAPPING** | A Metal API with equivalent semantics; the GL call becomes a Metal call. |
| **GENERATED_SHADER** | The fixed-function stage is reproduced by **generating MSL** that implements the spec's equations, driven by uniforms. |
| **GPU EMULATION** | Reproduced with additional GPU passes (extra render/compute passes, extra attachments). |
| **CPU EMULATION** | Reproduced on the CPU; the result is uploaded or fed back into the GL pipeline. |
| **HYBRID** | Partly GPU, partly CPU; the split is stated per mechanism. |
| **HARDWARE LIMITED** | Metal on A11 cannot do it natively. **Requires (a) capability evidence + (b) considered emulation options with rejection reasons.** |
| **BLOCKED** | No viable path identified. |

### 0.1 Status vocabulary (project/AGENTS.md §6)

`FULLY_IMPLEMENTED` · `PARTIAL` · `INCORRECT` · `STUB` · `MISSING` ·
`EMULATED` · `HARDWARE_LIMITED` · `BLOCKED` · `NOT_VERIFIED` ·
`NOT_APPLICABLE`.

**Environment labels:** `A11_DEVICE` · `SIMULATOR` · `OTHER_GPU` ·
`REFERENCE_ONLY` · `NONE`.

> **No A11 device was available while writing this document.** Every
> device-dependent statement below is `REFERENCE_ONLY` (Apple documentation) or
> `NOT_VERIFIED` (needs the probe in `docs/METAL_A11_CAPABILITIES.md` §4).
> Nothing here is labelled `A11_DEVICE`.

### 0.2 The five Metal facts that drive almost every decision

| # | Fact | Evidence |
|---|---|---|
| F1 | Metal's primitive vocabulary is **five** types: Point, Line, LineStrip, Triangle, TriangleStrip. No fan, no loop, no quad, no polygon, no adjacency. | `MTLRenderCommandEncoder.h:30-36` (`API_AVAILABLE(macos(10.11), ios(8.0))`) |
| F2 | Metal has **no line-width API at all** — `grep -rn "lineWidth" $SDK/.../Metal.framework/Headers/` → **0 hits**. | SDK header scan |
| F3 | Metal's **depth range is [0,1]**, framebuffer origin is **top-left**, and there is exactly **one viewport/scissor** per render pass on A11. | `MTLRenderCommandEncoder.h:281,338`; FST p.7 "Maximum number of viewports and scissor rectangles, per vertex function": Apple4 = **1** |
| F4 | Metal's flat interpolation takes the **first** vertex of the primitive; GL 4.x's default is the **last**. | Metal Programming Guide, "Graphics Rendering: Render Command Encoder": *"When rendering a triangle primitive with flat shading, the attributes of the **first** vertex (also known as the provoking vertex) are used for the whole triangle."* <https://developer.apple.com/library/archive/documentation/Miscellaneous/Conceptual/MetalProgrammingGuide/Render-Ctx/Render-Ctx.html> — corroborated by `metal2vulkan` (`docs/API.md`: *"Xbox uses 'last vertex', Metal uses 'first vertex'"*) and the gpuweb/GPUWeb issue 3180 summary. **NOTE: this contradicts `docs/LEGACY_TO_METAL_MAPPING.md` §1.5, which states Metal uses the last vertex — that document's §1.5 is wrong and its §1.5 "selected option" (duplicate the flat source vertex's colour on the CPU) is the right *response* to the correct fact.** |
| F5 | A11 = `MTLGPUFamilyApple4`. Hardware floor for: programmable blending Apple2, dual-source blending Apple2, programmable sample positions Apple2, argument buffers tier 1 Apple2, cube-map arrays Apple4, imageblocks/tile shaders/raster order groups Apple4, read-write textures Apple4, tessellation Apple3, counting occlusion query Apple3. | FST p.3-5 (hardware-family column); FST-2017 p.2 has a literal `iOS_GPUFamily4_v1` column |

| **Winding / `glFrontFace`** | **DIRECT MAPPING** | `setFrontFacingWinding:` (`MTLWindingClockwise`/`CounterClockwise`) + `setCullMode:` | GL's default front face is `GL_CCW`; Metal's default winding is CCW in a y-down space, which the Y-flip already accounts for. Correction needed in TGLMT: `GL_MAX_VIEWPORTS` must be reported as 1, not 16.** |
| **Scissor (single)** | **DIRECT MAPPING** | `setScissorRect:` | None | `src/metal/AppleMetalBridge.mm:946-949` |
| **`gl_FragCoord`** | **GENERATED_SHADER** | MSL's `[[position]]` fragment input is the window-relative position **with the pixel-centre +0.5 convention**, matching GL's `gl_FragCoord` after the Y flip | The Y direction differs (Metal's `[[position]].y` grows downward; GL's grows upward) — the converter must negate `y`. | MSL spec Table 5.5 (p.146): `position float4 — "Describes the window-relative coordinate (x, y, z, 1/w) values for the fragment"`; `include/tglmt/GLConvert.h` handles the flip |

| **Depth range `glDepthRange` / `glDepthRangeIndexed`** | **GENERATED_SHADER** | Depth range is folded into the same z-conversion as the clip-space range | GL 4.6 requires per-viewport depth ranges when `GL_VIEWPORT_INDEX` is used — not reachable on A11 (single viewport). | `src/gl/gl_get.cpp` tracks depth range; the range values are passed to the shader via `gl_DepthRange` (`src/gl/glsl_to_msl.cpp:10614`). **Status `PARTIAL`.** |

## 2. Polygon offset ↔ depth bias, depth clamp, stencil

| GL feature | Class | Metal mechanism | Semantic gap | Evidence |
|---|---|---|---|---|
| **`glPolygonOffset(factor, units)` / `glPolygonOffsetClamp`** | **DIRECT MAPPING** | `setDepthBias:slopeScale:clamp:` on the render command encoder | **Units differ.** GL: `offset = factor·DZ + r·units` where `r` is the minimum resolvable depth difference. Metal: `bias` is in **2⁻²⁴ depth units** (a fixed-point ULP, the same convention D3D uses) and `slopeScale` multiplies the maximum depth slope. TGLMT's mapping `units → bias` (unchanged) and `factor → slopeScale` is therefore *approximately* right only for a 24-bit-equivalent depth range; with a floating-point depth buffer or a non-unit depth range, the absolute offset differs. GL's `r` for `GL_DEPTH_COMPONENT24` is 1/(2²⁴−1); Metal's bias is 1/2²⁴. The difference is ~1 part in 16 777 216 — below the tolerance of any reasonable test, but it is a real difference. | `MTLRenderCommandEncoder.h:320`; TGLMT's own derivation at `src/gl/gl_apple_draw.cpp:2771-2796` ("Metal's depthBias is expressed in 2^-24 depth units … passing `units/2^24` here made every offset ~1.7e7 times too small and it vanished"). Status `PARTIAL` — needs a device test on A11 with a non-default depth range. |
| **`GL_POLYGON_OFFSET_CLAMP`** | **DIRECT MAPPING** | Metal's `clamp` parameter of `setDepthBias:slopeScale:clamp:` | Metal's convention is `clamp == 0` means *no clamp*, whereas GL's `glPolygonOffset` has no clamp parameter at all (the clamp is 0/unbounded) and `glPolygonOffsetClamp(f,u,0)` explicitly means "no clamp". These agree. | `src/gl/gl_raster.cpp:136-140`: *"glPolygonOffset không có tham số clamp: theo convention Vulkan/Metal, clamp==0 …"* |
| **Depth clamp (`GL_DEPTH_CLAMP`)** | **DIRECT MAPPING** | `setDepthClipMode:` with `MTLDepthClipModeClamp` | Metal clamps z to the **[0,1] clip volume**; GL's `GL_DEPTH_CLAMP` clamps to the **depth range** `[n,f]`. With the default range `[0,1]` these coincide. With a non-default `glDepthRange`, Metal's clamp is to [0,1] while GL's is to [n,f] — a divergence. | `MTLRenderCommandEncoder.h:314` (`API_AVAILABLE(macos(10.11), ios(11.0)`); enum `:63-66`; TGLMT `src/metal/AppleMetalBridge.mm:1005-1009`. GL 4.6 §17.4.3 defines the clamp against the depth range. **Status `PARTIAL`** for non-default depth ranges. |
| **Stencil test (front/back, 8 ops, ref, value mask, write mask)** | **DIRECT MAPPING** | `MTLDepthStencilState` (`MTLStencilDescriptor` per face) + `setStencilFrontReferenceValue:backReferenceValue:` | TGLMT currently sets **only one** reference value (`setStencilReferenceValue:`), with the comment *"Metal 1 ref cho cả 2 mặt"*. Metal since iOS 9.0 has the two-value form, so this is fixable on A11. | `MTLRenderCommandEncoder.h:468` `setStencilFrontReferenceValue:backReferenceValue:` `API_AVAILABLE(macos(10.11), ios(9.0))`; TGLMT `src/metal/AppleMetalBridge.mm:957-960`. **Status `PARTIAL` — implementation gap, not a hardware limit.** |
| **Stencil in a separate attachment** | **DIRECT MAPPING** | `MTLRenderPassStencilAttachmentDescriptor` | A11 supports separate depth and stencil attachments (FST p.3, hardware family Apple2). | `MTLRenderPass.h`; TGLMT keeps `depth_`/`stencil_` separately (`src/metal/AppleMetalBridge.mm:770-771`) |
| **Alpha test (`glAlphaFunc`, GL 1.x)** | **GENERATED_SHADER** | `discard_fragment()` in the fragment shader based on the interpolated alpha | Exact: GL's alpha test is a fragment-level predicate. | GL 4.6 core **removed** `glAlphaFunc` (core profile); this is a compatibility-profile feature. `docs/LEGACY_TO_METAL_MAPPING.md` §7.1 already specifies it as GENERATED_SHADER. |
| **`GL_COLOR_LOGIC_OP`** | **HARDWARE LIMITED** (bitwise op) / **GPU EMULATION** (the feature) | *No blend operation performs a bitwise op.* `MTLBlendOperation` = {Add, Subtract, ReverseSubtract, Min, Max, Unspecialized} — the 16 GL logic ops (`CLEAR, AND, AND_REVERSE, COPY, AND_INVERTED, NOOP, XOR, OR, NOR, EQUIV, INVERT, OR_REVERSE, COPY_INVERTED, OR_INVERTED, NAND, SET`) are not expressible. | TGLMT **bypasses** the blend stage when `GL_COLOR_LOGIC_OP` is on (`src/gl/gl_apple_draw.cpp:2320-2322`) but **never performs the operation** — the destination keeps its old value. That is a *silent wrong answer*, which the project forbids. | **(a) Capability:** `MTLRenderPipeline.h:53-64` — `MTLBlendOperation` has exactly six values, none bitwise; the MSL specification has no logic-op builtin; `grep -rn "logicOp" $SDK/.../Metal.framework/` → 0 hits. FST p.3 puts "Programmable blending" at hardware family **Apple2** — i.e. **framebuffer fetch IS available on A11**. <br> **(b) Emulation options:** 1. *Leave it unimplemented (TGLMT's current behaviour).* **Rejected**: it produces a silently wrong framebuffer, which violates the project's honesty rules; `docs/METAL_A11_LIMITATIONS.md` §2.7 already flags it. 2. *Two-pass: render the source to an offscreen texture, then a full-screen pass that reads both source and destination and writes the logical result.* **Selected.** Correct and always available. Cost: one extra full-screen pass + one extra texture per logic-op draw, and the logic-op draws must be isolated from the surrounding batch (a "path change", not a pipeline-key change). 3. *Programmable blending / framebuffer fetch: read the destination colour in the fragment shader via `[[color(0)]]` as an **input**, compute the logical op, and write the result.* **This is the good one and TGLMT does not use it.** Evidence it is available on A11: FST p.3 "Programmable blending \| Metal 3 & 4 \| **Apple2**"; FST-2017 p.2 shows "Programmable blending" ✓ in the `iOS_GPUFamily4_v1` column; the Metal Programming Guide's "Programmable Blending" section and WWDC19 "Modern Rendering with Metal" describe exactly this (fragment shaders read back the value of the pixel they are writing, from tile memory). Constraint from WWDC19: *"when you are using programmable blending, you cannot access the depth attachments"* — so the logic-op path must not need depth/stencil in the same pass, or must use the two-pass fallback. **Status: `HARDWARE_LIMITED` for the *blend-stage* implementation; the *feature* is emulable — `GPU EMULATION` via programmable blending (single pass) with the two-pass form as the universal fallback. NOT a `BLOCKED`.** |

## 3. Rasterisation, primitives and shading

### 3.1 Primitives without a Metal equivalent

| GL feature | Class | Metal mechanism | Semantic gap | Evidence |
|---|---|---|---|---|
| **`GL_TRIANGLE_FAN`** | **CPU EMULATION** | Expand to `GL_TRIANGLES` on the CPU and issue `drawIndexedPrimitives:MTLPrimitiveTypeTriangle` | Cost O(n) CPU + an index upload per draw. Correct output. TGLMT's expansion bails out when `baseVertex != 0` (`:1960`, indexed) — that path is `MISSING`, not a hardware limit. | F1; TGLMT `src/gl/gl_apple_draw.cpp:1935-1975` |
| **`GL_LINE_LOOP`** | **CPU EMULATION** | Expand to `GL_LINE_STRIP` + repeat the first index | Same cost. Same `baseVertex != 0` bail-out (`:1990`, indexed). | F1; `src/gl/gl_apple_draw.cpp:1977-2004` |
| **`GL_QUADS`, `GL_QUAD_STRIP`** | **CPU EMULATION** | Triangulate on the CPU (quad → 2 triangles; quad-strip → alternating triangles) | **Not implemented in TGLMT at all** — the draw path only maps modes 0x0000/1/2/4/5 (`src/gl/gl_apple_draw.cpp:2008-2012`); `GL_QUADS` (0x0007) and `GL_QUAD_STRIP` (0x0008) fall through to a default that is not a Metal primitive. GL 4.6 core has no quads (they are compatibility-profile only, GL ≤ 2.1 / `GL_QUADS` retained in the compatibility profile), so this is a **compatibility-profile gap**, not a core-profile one. | F1; `docs/khronos/gl.xml` (GL_QUADS removed in GL 3.0 core) |
| **`GL_POLYGON`** | **CPU EMULATION** | Ear-clipping triangulation of the boundary polygon | Same as above; compatibility profile only. GL core ≥3.0 has no polygon primitive. | F1; GL 4.6 core removed `GL_POLYGON` |
| **Adjacency primitives** (`GL_LINES_ADJACENCY`, `GL_LINE_STRIP_ADJACENCY`, `GL_TRIANGLES_ADJACENCY`, `GL_TRIANGLE_STRIP_ADJACENCY`) | **CPU EMULATION** | Filter the index stream to the non-adjacency positions, then draw as lines/triangles | Adjacency primitives exist in the **compatibility** profile (GL ≤ 3.0, `GL_ARB/EXT_geometry_shader4`); GL 4.6 core removed them. Also note the *adjacency primitives that a **geometry shader** would emit* are a different thing (see §3.5) — Metal's `drawPatches`/`drawPrimitives` cannot emit adjacency either, so a GS-emulation design must avoid generating adjacency output or must convert it. | F1; GL 4.6 core removed adjacency primitives |
| **Primitive restart (`GL_PRIMITIVE_RESTART_INDEX`)** | **CPU EMULATION** | Split the draw into runs at the restart index and issue one Metal draw per run | O(n) CPU + a readback of the index buffer per draw. TGLMT stores the restart index (`src/gl/gl_draw.cpp:575`) but does **not** split the draw on the GPU path. Metal has no restart index: `grep -rn "restart" $SDK/.../Metal.framework/Headers/` → **0 hits**; `drawIndexedPrimitives:` has no restart parameter (`MTLRenderCommandEncoder.h:732`). | **(a) Capability:** no restart API in the SDK headers. **(b) Options:** 1. *Rewrite the index buffer on the CPU, splitting runs.* **Selected** — exact, and the CPU already rewrites indices for `baseVertex` (see §4). Cost O(n) per draw. 2. *Use `MTLIndirectCommandBuffer` with one command per run.* Rejected as a *first* implementation: the run boundaries are not known until the index buffer is read, so the ICB would have to be rebuilt on the CPU anyway — same cost, more machinery. It is a valid optimisation *after* the CPU split exists. **Status: `HARDWARE_LIMITED` (native), emulated via CPU index rewriting.** |

### 3.2 Rasterisation state

| GL feature | Class | Metal mechanism | Semantic gap | Evidence |
|---|---|---|---|---|
| **Line width > 1** | **HARDWARE LIMITED** (native) / **CPU EMULATION** (feature) | *No line-width API exists.* | GL core clamps `glLineWidth` to the implementation's aliased range. TGLMT reports `GL_ALIASED_LINE_WIDTH_RANGE` = (1,1) (`src/gl/gl_get.cpp:353, 527, 593`) — conformant, since GL 4.6 §14.6.4 leaves the range implementation-dependent. | **(a) Capability:** `grep -rn "lineWidth\|LineWidth" $SDK/.../Metal.framework/Headers/` → **0 hits**; `MTLRenderPipelineDescriptor` has no line-width property (full property list read: `MTLRenderPipeline.h:179-307`); FST has no line-width row at all. **(b) Options:** 1. *Reject `glLineWidth > 1` with `GL_INVALID_VALUE`.* Conformant in the **core** profile (GL 4.6 App. E.2: *"values greater than 1.0 will generate an INVALID_VALUE error"*) but wrong for the **compatibility** profile, where wide lines are legal. 2. *Expand each segment into a quad (triangle strip) on the CPU.* **Selected for the legacy/compatibility profile.** Exact for the segment body; the classic divergence is **joins and caps** — a naive quad-per-segment leaves gaps at convex joins and overdraws at concave joins; a mitred-join implementation is required for exactness. 3. *Use MSAA to fake width.* Rejected: MSAA is a spatial antialiasing mechanism, not a width mechanism. **Status: `HARDWARE_LIMITED` natively; `CPU EMULATION` planned for the compatibility profile (mitred joins + documented cap behaviour).** The existing `docs/LEGACY_TO_METAL_MAPPING.md` §7.5 reaches the same conclusion with the same evidence — **consistent**. |
| **Point size (`glPointSize`)** | **DIRECT MAPPING** (≤511 px) | MSL `[[point_size]]` on the vertex output; the device maximum is **511** | Metal's point size is a **vertex-shader output**, so the size varies per vertex — which is exactly GL's model. The 511-px cap must be enforced by the app (GL's `GL_POINT_SIZE_RANGE` is implementation-dependent). | MSL spec Table 5.4 (p.143) `point_size float — "Size of a point primitive"`; FST p.8 "Maximum size of a point primitive" = **511** for every family including Apple4. **Correction: `MTLRenderPipelineDescriptor` has NO `maximumPointSize` property** — `grep -rn "maximumPointSize" $SDK/.../Metal.framework/` → **0 hits**; the 511 limit is a device limit. TGLMT currently emits `[[point_size]]` only in the TCS/TES paths (`src/gl/glsl_to_msl.cpp:4717, 4774`); the ordinary raster path does not plumb `GL_POINT_SIZE` → **status `PARTIAL`**. |
| **Line smoothing (`GL_LINE_SMOOTH`)** | **CPU EMULATION** | Expand lines to quads and apply analytic coverage in the fragment shader (or use MSAA) | GL's aliased/smooth distinction is a rasterisation-quality knob, not a semantic one; a smooth-quad expansion is visually equivalent. | GL 4.6 core **removed** `GL_LINE_SMOOTH` (compatibility profile only) |
| **Point smoothing (`GL_POINT_SMOOTH`)** | **GENERATED_SHADER** | Round the point to a circle in the fragment shader using `[[point_coord]]` | `[[point_coord]]` gives the 0..1 position within the point sprite — exactly the input needed. | MSL spec Table 5.5 (p.146) `point_coord float2 — "Two-dimensional coordinates, which range from 0.0 to 1.0 across a point primitive"` |
| **Polygon stipple (`glPolygonStipple`)** | **GENERATED_SHADER** | A 32-byte pattern in a uniform buffer; the fragment shader computes the screen-space parity and `discard_fragment()` | GL's stipple pattern is defined in **window coordinates**, so it must be evaluated per fragment against `gl_FragCoord`, not per primitive. Exact if the pattern is evaluated on the fragment's window position. | GL 4.6 core removed stippling (compatibility profile only); `docs/LEGACY_TO_METAL_MAPPING.md` §7.2 already specifies GENERATED_SHADER |
| **Line stipple (`glLineStipple`)** | **GENERATED_SHADER + CPU EMULATION** | Expand the line to a quad with a "distance along the line" attribute; the fragment shader evaluates the 16-bit pattern and discards | Metal's line rasteriser gives the fragment shader no position *along* the line, so the pattern cannot be evaluated without the expansion. The pattern must reset per segment. | GL 4.6 core removed it; `docs/LEGACY_TO_METAL_MAPPING.md` §7.4 specifies exactly this |

### 3.5 Geometry shaders — **emulation is mandatory, not optional**

`project/AGENTS.md` §6 / **D-018**: *"Geometry shader phải có emulation chạy được —
không được kết luận `HARDWARE_LIMITED`."* So this section specifies the
emulation and does **not** conclude `HARDWARE_LIMITED`.

**Current TGLMT behaviour:** a program with a geometry stage is refused at draw
time — `src/gl/gl_apple_draw.cpp:1901-1904` returns `false` after logging
*"AppleDrawGL: GS trace-only (M5b-future)"*, and `src/gl/gl_program.cpp:495`
flags the stage as "Metal không native → cờ fallback". So today a GS program
**draws nothing**: that is `MISSING`, not `HARDWARE_LIMITED`.

#### 3.5.1 The emulation design

Metal has no geometry shader and no mesh shader on A11
(mesh shading is hardware family **Apple7** — FST p.5 — and
`supportsMesh()` in TGLMT already returns `supportsFamily:MTLGPUFamilyApple7`,
`:2296-2299`). But Metal *does* have everything needed to emulate one:

| GL GS capability | Metal mechanism available on A11 | Evidence |
|---|---|---|
| Run a shader once per **input primitive** | **Compute kernel** dispatched over primitives; the kernel reads the primitive's vertices from a buffer | `dispatchThreadgroups:threadsPerThreadgroup:` — iOS 8.0, all families |
| Read the input primitive's vertices | A `device` buffer holding the VS output (the same buffer the VS writes for transform feedback) | FST p.4 "Read/write buffers in functions \| Apple3" |
| Emit a **variable** number of vertices | `atomic_fetch_add_explicit` on a counter in a device buffer to reserve a slot range | Metal atomics on buffers are Metal 1 / Apple2+; **texture** atomics are Apple6 (FST p.5) and must not be used |
| Emit **line/triangle/point** output | A compute kernel writes into three separate output regions, one per primitive type | — |
| Control the **primitive order** | An atomic ticket counter (`atomic_fetch_add`) gives each GS invocation a monotonically increasing primitive id; the index-building pass then emits primitives in that order | — |
| Rasterise the emitted geometry | A second pass: a compute kernel builds an index buffer from the emitted vertex range, then `drawIndexedPrimitives:` with the right `MTLPrimitiveType` | F1 |
| `gl_PrimitiveID`, `gl_InvocationID` | `[[thread_position_in_grid]]` / the ticket counter | — |
| `EmitVertex`/`EndPrimitive` semantics | A per-primitive "end" flag in the emitted stream, interpreted by the index-building kernel | — |

#### 3.5.2 Why not the alternatives

| Alternative | Rejected because |
|---|---|
| **Metal mesh shaders** | Hardware family **Apple7** (FST p.5) — A11 is Apple4. Also iOS 16 API (`MTLDevice.h:830`), and mesh shading requires Metal 3 hardware. **Not available on A11.** |
| **A second vertex-shader pass** | A VS cannot read its *own* neighbouring vertices or emit a variable number of vertices; it has no primitive-level addressing. |
| **Tessellation as a GS proxy** | Metal's tessellation is fixed-topology: it subdivides patches, it cannot reorder, discard, or change the topology of an arbitrary input primitive. A GS can change the primitive type and count arbitrarily. |
| **Reject GS programs** | This is TGLMT's current behaviour and it is a *missing implementation*: GS is part of the GL 4.6 **core** profile, so rejecting it makes TGLMT non-conformant for a large, commonly used part of the API. **Rejected as the final answer; must be replaced by the compute-based emulation.** |

#### 3.5.3 Status

**`MISSING` today; the compute-based emulation above is the specified design.**
The GS emulation requires:

1. The VS must write its outputs to a **device buffer** (TGLMT already does this
   for transform feedback — `src/gl/gl_apple_draw.cpp:1421+`).
2. A **GS compute kernel** generated from the GLSL GS source, dispatched with
   one invocation per input primitive.
3. An **index-building compute kernel** that consumes the emitted vertex stream
   and produces a per-type index buffer plus the draw ranges.
4. One `drawIndexedPrimitives:` per emitted primitive type, using
   `MTLPrimitiveTypePoint`/`Line`/`LineStrip`/`Triangle`/`TriangleStrip`.

**Costs / risks:** the VS output must be buffered (memory + bandwidth) even for
draws that would not otherwise need it; the primitive order must be preserved
via a ticket counter (which serialises the kernel's atomic contention); and
`gl_PrimitiveIDInRange` / `gl_PrimitiveID` semantics need the ticket, not
`[[primitive_id]]` (Metal's `primitive_id` is **Apple7+** — FST p.5 — and is
therefore **not** available on A11).

## 9. Legacy (OpenGL 1.x) feature groups — pointer

`docs/LEGACY_TO_METAL_MAPPING.md` already covers the 1.x fixed-function pipeline
in depth (lighting, fog, texture environment, display lists, evaluators,
selection, feedback, matrix stacks, …). **That document is not rewritten here.**
The only points where this document's conclusions **differ** from it are
recorded below, with the evidence.

| Topic | `LEGACY_TO_METAL_MAPPING.md` says | This document says | Evidence |
|---|---|---|---|
| **Metal's provoking vertex** | §1.5: "MSL `[[flat]]` takes the provoking vertex, which for Metal is the **last** vertex of the primitive" | **Metal takes the FIRST vertex.** | The Metal Programming Guide: *"When rendering a triangle primitive with flat shading, the attributes of the **first** vertex (also known as the provoking vertex) are used for the whole triangle."* <https://developer.apple.com/library/archive/documentation/Miscellaneous/Conceptual/MetalProgrammingGuide/Render-Ctx/Render-Ctx.html>. Corroborated by `metal2vulkan` docs/API.md ("Xbox uses 'last vertex', Metal uses 'first vertex'") and by ANGLE's Metal backend, which rewrites the index buffer precisely to *impose* GL's last-vertex rule. **The legacy document's §1.5 "selected option" (duplicate the flat source vertex's colour on the CPU) is the correct response to the correct fact — it just states the premise wrongly.** |
| **Programmable blending** | §1.1: "**Programmable blending** \| Metal 3 & 4 only … the A11 runs Metal 2, so the API is not reachable" | **Programmable blending (framebuffer fetch) IS available on A11.** | FST-2017 p.2 shows "Programmable blending" ✓ in the `iOS_GPUFamily4_v1` column; FST p.3 puts the hardware family at **Apple2**.
